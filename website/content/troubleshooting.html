05 / DIAGNOSE

Find the failing layer.

Separate configuration errors from build failures, activation issues, and hardware behavior.

Configuration and evaluation

Nix says a file is not tracked by Git

Git-backed flakes do not normally include untracked files. Review and add your new module files, then evaluate again. The profiles/local.nix and profiles/local/ paths are intentionally ignored; explicitly track only reviewed configuration with git add -f, or use a different profile name. Never stage secrets in plaintext.

The flake output does not exist

Match your selected output to its exact definition in flake.nix. The Makefile has maintainer-specific defaults: override MACOS_CONFIG, LINUX_CONFIG, or VM_CONFIG for your own host. Do not assume a legacy script target is exported by the current flake.

An option was removed or renamed

Inspect the error and the module it names. Compare flake.lock with your previous working revision, then check the documentation for that dependency revision. Resolve the option mismatch before activation.

Builds and activation

A build targets an unsupported system

Check whether the derivation targets Darwin or Linux, and ARM64 or x86_64. Building a Linux system from macOS may require a configured Linux builder. For Apple Silicon guests, consider the documented ARM64 ISO and UTM installation workflow.

Setup refuses to change the system

The Makefile intentionally requires CONFIRM_APPLY=1 for activation. Finish your own profile, hardware, and secrets setup first; then use the platform-specific command with your output name.

Agenix cannot decrypt a secret

Check that the file was encrypted to your public recipient key, that the host can access the matching private identity, and that the declared paths match. The maintainer's encrypted files are not usable by a new fork.

A configuration change breaks normal use

Stop applying additional changes. Use a known working generation or revision appropriate to your platform, then inspect the failing diff. Keep recovery access available before changing boot, networking, or graphics configuration.

VM and hardware checks

Start by inspecting QEMU's platform configuration:

./scripts/qemu-config.sh config
./scripts/qemu-config.sh test x86_64

Confirm the guest architecture, allocated RAM and disk space, acceleration support, and SSH endpoint. On Linux, inspect /dev/kvm and your user's access to virtualization. For passthrough, check actual device IDs and IOMMU groups before changing driver binding.
